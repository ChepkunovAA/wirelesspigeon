# Тестирование

## 1. Слои тестов

| Слой | Где живёт | Инструменты | Цель |
|------|-----------|-------------|------|
| Unit | `*/src/test/java` рядом с сервисом | JUnit 5 + Mockito | Логика сервисов в изоляции |
| Интеграционные | `webapp/src/test` | `@SpringBootTest` + MockMvc (+ реальная БД через Docker) | Сквозные сценарии, MVC-шаблоны, CSRF, роли |

Подход (AGENTS.md): «unit-тесты сервисного слоя до реализации», стиль —
как в `wishlist/src/test`.

## 3. БД под интеграционными тестами

- Интеграционные тесты используют реальный PostgreSQL (обычно — поднятый
  Docker-контейнер `corpsman-postgres`). Скрипты/файлы тестов пишут
  временные данные в `/home/albert/Project/tmp/` (например, `tmp/test.log`).
- Тесты полагаются на автоматическую инициализацию схемы через Liquibase.

## 4. Команды

```bash
mvn test                                  # все модули (≈ 5,5 мин)
mvn clean install                         # сборка + тесты
mvn test -pl webapp -am                   # webapp + зависимости
mvn -q install -DskipTests && mvn test -pl forum   # быстрая точечная
```

Слишком долго (342 с)? — см. `getting-started.md` → «Сборка и тестирование»
(правило stale-jar, `-T 1C` не использовать).

## 5. Проверка успеха

Успешный прогон: `[INFO] BUILD SUCCESS`, при этом должно быть
`Tests run: 460, Failures: 0, Errors: 0` (на релиз 2.2.0).

```bash
mvn test -pl webapp -am > /home/albert/Project/tmp/test.log 2>&1
grep "BUILD" /home/albert/Project/tmp/test.log | tail -1
```

## 6. Правила добавления тестов

1. Тестируйте **сервисный слой** (unit) до/вместе с реализацией.
2. Интеграционные сценарии — в `webapp` (там есть MVC-шаблоны и
   подключение БД).
3. Не дублируйте тесты (см. AGENTS.md «Избегай дублирования тестов»).
4. Добейтесь зелёных unit-тестов до запуска интеграционных из webapp.
5. Если тест требует доступа к анонимным/гостевым сценариям — учитывайте
   новую матрицу (аноним GET /forum = 200, POST = 302, без CSRF = 403).

## 7. E2E RPG-листа по HTTP (релиз 3.1.0)

Сценарий также проверяет библиотеку систем: публикация с составом параметров и
выбором вида списка, сохранение анкеты в БД, перенос анкеты в параметры игры
(ведущий не заполняет вручную), пробный лист с составом системы и без
сохранения, отсутствие ложной фразы «настраивает ведущий»; оба типа списков,
правку инвентаря из просмотра, недоступность `lists/{key}/add|remove`,
скрытие кнопки «Системы» от анонимного и ссылку «Редактировать лист» на
существующий лист, предвыбор системы из ссылки «Создать игру на этой системе»,
форк через форму создания с предзаполнением (`?forkFrom=`, перенос состава,
приватность, автор копии, отсутствие копии до отправки формы), приватность при
снятой галочке «Публичная система» и на форме игры при снятой галочке «Игроки
видят все параметры листа друг друга», отсутствие бейджа версии и колонки
`system_version`, отсутствие поля «Порядок» в форме и в таблице состава с
простановкой позиций сервером, форк у чужой публичной системы при отсутствии
правки и удаления у чужого пользователя, права автора на правку/удаление и отказ
чужаку (403), отсутствие кнопки «Не сохраняется» в предпросмотре, надпись «К играм»,
а также отсутствие избыточной подсказки в форме публикации.

Сценарий проверяет бизнес-логику на живом контейнере, а не только его запуск:

1. регистрация мастера и игрока по инвайт-ключу, логин;
2. мастер создаёт D&D-игру, игрок подаёт заявку, мастер её принимает;
3. просмотр листа: пустые класс/раса/предыстория выводятся с `—`;
4. блок «Ячейки» один, нулевые уровни скрыты, `текущее / максимальное` одной
   строкой, нет отдельных разделов «Ячейки N ур.»;
5. правка списков возможна только из формы редактирования: элемент с
   заголовком/описанием/уровнем сохраняется через `listJson`, группируется
   по уровню, а в просмотре нет ни кнопок, ни модалок, ни форм;
6. заклинание с уровнем 3 попадает в группу «Ур. 3», группы идут по
   возрастанию;
7. форма редактирования: блок «Ячейки» со скрытыми полями и кнопками
   `+/-` (`data-slot-step`, `data-max-step`) для **всех 9 уровней**,
   предупреждение `data-slot-warning`, кнопка «Восстановить», у простого
   списка карточки с полем ввода и кнопкой «+», у сложных — модальные окна
   `list-add-modal-inventory` / `list-add-modal-spells`, подсказка
   «(с заголовком и описанием)» отсутствует;
8. `POST .../edit` с `attributes[i].listJson` сохраняет заголовок и описание;
9. ячейки нового уровня (5) задаются из формы редактирования и появляются
   в просмотре, соседний пустой уровень (6) остаётся скрытым;
10. `POST spell-slots-reset` реально обновляет БД (проверка `psql`);
11. предупреждение появляется при `current > max` и в просмотре;
12. со страницы игр есть переход в библиотеку систем, а при создании игры
    выбирается система из библиотеки (в том числе после ошибки валидации).

Дополнительно проверяется, что удалённые эндпоинты правки списков
(`lists/{key}/add|remove`, `inventory-add|remove`) отвечают 404, а
существующий `spell-slots-reset` на тех же данных — 302.

Аккаунты — только с префиксом `auto_`. Скрипты: `tmp/e2e/`
(в `.gitignore`, для прогона заново нужен пересозданный инвайт-ключ).

## Клиентские проверки в браузере (релиз 3.2.0)

Часть правок живёт только в JS страницы: правка денег без перезагрузки,
стрелки числовых полей, добавление строк в анкете системы. Такое нельзя
проверить ни HTTP-запросом, ни разметкой — нужен настоящий браузер.

Сценарии лежат в `tmp/ui/` (в `.gitignore`) и гоняются через geckodriver и
системный Firefox — без установки тяжёлых пакетов в проект:

| Скрипт | Что проверяет |
|--------|---------------|
| `tmp/ui/check_money.py` | кнопки `±` и обмен денег в просмотре листа: значение меняется, страница не перезагружается, кнопки работают после нескольких обменов |
| `tmp/ui/check_validation.py` | выбор подтипа текстового поля в анкетах игры и системы, значение по умолчанию в списке, пункт «Другое» в пробном листе, блокировка кнопки сохранения при неверном значении |
| `tmp/ui/check_money.py` | анкета системы (значение по умолчанию, флаг ручного ввода), текстовое поле с пунктом «Другое», шаг числового поля за нижней границей, кнопки числовых полей в пробном листе |

Подготовка: `mvn -q install -DskipTests`, `docker compose up -d --build app`,
`bash tmp/e2e/reset.sh && bash tmp/e2e/e2e.sh` (создаёт аккаунты `auto_e2e_*`),
geckodriver в `tmp/bin/geckodriver`, selenium в окружении `../.venv-ui`.

Подготовка данных: `bash tmp/ui/make_custom_game.sh "<название>"` создаёт
игру с анкетой и листом игрока (`<gameId> <sheetId>`),
`bash tmp/ui/make_dnd_game.sh` — игру на D&D с блоком денег.

Условие запуска: `UI_SHEET_PATH=/rpg/games/{id}/characters/{sheetId}` для
`check_money.py`.

Правило: `fetch` с телом-строкой обязан слать явный
`Content-Type: application/x-www-form-urlencoded`, иначе сервер не разберёт
параметры — это ловится только в браузере (см. `frontend.md`).
